# The `review_after:` freshness key — one optional date, accession views as pure projection (`frontmatter@3` proposal)

_Filed from the `vlt-core` vault out of the **2026-07-06 vault-evolution run** (gap analysis → brainstorm → six parallel pressure-tests → synthesis, vault commit `ef2cce6`). Two independently-flagged gaps — no queryable ingestion/provenance record (asked for separately by both Librarian and Researcher) and no freshness mechanism for time-sensitive pages (stale World Cup / NFL draft / policy-deadline pages) — collapsed under pressure-testing into **one optional frontmatter key** plus a zero-schema Obsidian Base. This is also the first real exercise of the `{overlays}/*.overlay.md` + `vlt-upgrade` merge-not-replace machinery — the local-prototype-then-upstream rail's first full round trip — so it doubles as a test filing for that mechanism. Siblings in this batch: `2026-07-06-091004-no-boundary-without-a-bell.md` (shares the `review_after` deferral vocabulary), `2026-07-06-091005-write-verification-attestation.md` and `2026-07-06-091003-enforcement-kit-derive-first.md` (share the frontmatter/schema surface)._

**Filing status.** The pressure-test plan scheduled this filing *after* the first review cycle (its M5 milestone); it is being filed **now at the owner's request as a design-stage proposal**. The schema decision is final — one key, resolved date, absence = evergreen, delivered locally via the vault's first convention overlay. The first review-cycle evidence (does the Due-for-review queue actually get worked, or does it silently age?) follows in a supplementary note once the cycle completes.

**Update (2026-07-06, owner ruling — supersedes the base-packaging shape below).** The vault will land the Register / Due-for-review / Horizon views as **new views inside the existing vault-grown `wiki.base`** (same population — `type == "wiki"` — one filter definition, one lens-set), not as a separate `ledger.base`. The accession-register *naming* rationale is retained below for the record but overridden. Consequences: the local prototype becomes a `wiki.base` edit; change 5's shipped-base + `bases:` structure-map row drops from the recommended path; open question 1 tilts to its third option (Bases stay vault-local; the module ships only the schema + skill lines, with the three views as documented reference).

## Problem statement + evidence

- **No cross-page accession view** (gap-analysis weakness 3, tagged `module`). 13 ingests in two weeks in `vlt-core` and no queryable record of what entered the wiki from where, when, at what trust. Both Librarian and Researcher flagged this independently, in different vocabularies; it sat in `_agent/backlog.md` as a capability gap. The data was never missing — every one of the 122 wiki pages carries `sources:`, immutable `created:`, and `trust:`, and `_agent/log.md` holds the per-event narrative — it was just scattered across three non-queryable forms.
- **No freshness mechanism** (weakness 8, tagged `both`). World Cup, NFL-draft, and policy-deadline pages passed their events without `[!stale]` markers. The root defect: the schema **conflates edit recency with content validity** — `last_updated` is what `vlt-lint` reads to judge staleness, but a page can be untouched *and* current (evergreen) or untouched *and* expired (pricing, deployment timelines, dosing guidance), and nothing distinguishes the two. Staleness today is a lint *hunt* (cross-checking `last_updated` + mtime against newer research notes) instead of a page-announced *queue*.
- Five-Whys root cause (pressure-test): the frontmatter schema captures **catalog** fields but no **accession/condition** fields — library science separates the accession record (when/whence/condition acquired) from the catalog record (what it is); the vault built only the catalog half.

## The decision and its rationale

The original idea proposed three keys (`ingested_from`, `shelf_life`, `review_after`) plus generated views. Pressure-testing against the live vault shrank it to **one**:

1. **The ledger needs no schema change at all.** An accession register is a pure Obsidian Base projection over fields every wiki page already carries — `created` / `sources` / `trust` / `category` / `last_updated`. `ingested_from` **duplicates `sources:`** and was dropped (never add a key whose content another key already carries).
2. **Store the resolved date, not the duration.** `review_after: YYYY-MM-DD` beats `shelf_life: 6mo`: the query surface (Bases) consumes dates directly, and the duration judgment belongs at write time in the ingesting partner's head, not in the schema. One key, not two. This deliberately matches the deferral schema in the sibling bell filing (`…-091004-…`) — `review_after` there is likewise a **resolved date, never a duration** — so the module ends up with one `review_after` vocabulary, not two.
3. **Absence is the semantics.** No `review_after` = evergreen. Only genuinely time-sensitive pages carry it, so 100+ evergreen legacy pages generate zero noise and backfill degrades gracefully — the 122-page migration is a non-event by construction.

**Rejected alternatives** (documented in the pressure-test; listed so they aren't re-litigated):

- Append-only `accessions.md` file — reintroduces the dual-write failure mode the idea set out to kill.
- Script-generated ledger parsing `{log}` prose — brittle; retained only as the documented **escape hatch** if per-source accession dates are ever truly needed (never nested YAML — flat-YAML rule 3 makes per-source structured records unrepresentable by design).
- SQLite accession DB — violates the plain-markdown ethos.
- `shelf_life` duration + lint computes due dates — moves computation into every lint run; pages should announce their own expiry.
- **Trust-decay** (auto-demote `trust:` on expiry) — the most instructive rejection: trust is a *human-review* axis, freshness is a *world-change* axis; a `verified` page can expire and a `raw` page can be evergreen. They stay orthogonal (provenance ≠ condition ≠ appraisal).
- Per-source flat strings (`"url @ date"`) inside `sources:` — pollutes a field every consumer reads.
- New views inside the existing `wiki.base` — a separate `ledger.base` names the accession concept and keeps `wiki.base` a scanning tool. **(Reversed by the 2026-07-06 owner ruling above — the naming rationale lost to one-population-one-base.)**

**v2 candidates parked deliberately** (do not ship in `frontmatter@3`): `source_type:` (url/book/paper — the accession "format" facet, cheap Register grouping) and `review_note:` ("what to check" hint).

**Local prototype (vlt-core — planned, not yet minted):** Register / Due-for-review / Horizon views added to the existing `_agent/bases/wiki.base` (per the owner ruling above; an ungated agent-zone edit); `review_after` to be appended to `_agent/conventions/frontmatter.overlay.md` via a council-gated `vlt-mint` convention edit — **the vault's first overlay** once it lands (today `_agent/bases/` holds only `wiki.base`, and `_agent/conventions/` only `.baseline/`); seeded Librarian backfill capped at ~10–15 clearly time-sensitive pages, then on-touch steady state. `vlt-ingest` will need no local skill edit — it reads `{conventions}` before writing, so the key flows in through the convention itself (but see latent bug 1).

In *Wiki pages (`{wiki}`)*, add one **optional** key to the schema block plus a semantics paragraph: `review_after: YYYY-MM-DD` — the date content validity should be rechecked; a **resolved date, never a duration**; **absence = evergreen**; set at write time only when content is time-sensitive (pricing, versioned tools, deployment/event timelines, dosing/health guidance, market state); on review exactly one of three legal outcomes — bump the date, mark specific claims `[!stale]` per `wiki-supersession.md`, or remove the key (page proved evergreen). 3. **`skills/vlt-lint/SKILL.md`** — bump `depends_on` to `frontmatter@3`; add a Step 2 finding: **`review_after` in the past** → report under `flag_for_human` as a new `review_due:` key (page + date). Never auto-fix — the three-outcome review is judgment work. This gives the existing "`[!stale]` handling" check a mechanical trigger instead of prose-parsing for time-bound claims; note in Step 2's stale-claims bullet that a page carrying `review_after` announces its own expiry (no `last_updated`-vs-mtime inference needed).
4. **`skills/vlt-setup/assets/workflows/vlt-lint-full.js`** — add `review_after` to the per-page finding schema so the full-mode fan-out reports past-due pages (per the convention-coherence rule, `vlt-lint`'s ack covers this workflow asset).
5. **The three views** — per the 2026-07-06 owner ruling, vlt-core folds these into its vault-grown `wiki.base`, and open question 1 tilts to shipping **no** base file (schema + skill lines only, views as documented reference): **Register** (page, created, sources, trust, category, last_updated; sorted `created` DESC), **Due for review** (`review_after` set AND `review_after <= today` — verify Bases date-comparison syntax before shipping; see open question 2), **Horizon** (`review_after` set, sorted ASC). If the module later decides to ship a base after all, the original packaging shape stands: new asset at `skills/vlt-setup/assets/bases/ledger.base`, a `bases: _agent/bases/` row in the canonical `vault_structure` default map at `skills/vlt-setup/assets/module.yaml` (the declared single source of truth for logical paths — the SKILL.md path table is illustrative only; touch it secondarily as documentation, consistent with `2026-07-06-091003-…` change 1), and a **create-if-absent** provisioning step (same discipline as `{backlog}` — never clobber a vault's customized views).
6. **`skills/vlt-upgrade/SKILL.md`** — the overlay-subsumption check described under Migration below.

## Upgrade / migration path for existing installs

- **A vault carrying the local overlay (vlt-core's case once the local mint lands).** On upgrade to the version shipping `frontmatter@3`, the base refresh delivers a `frontmatter.md` that now *contains* `review_after` — and the vault's `frontmatter.overlay.md` would still carry its own definition. Today's machinery preserves overlays verbatim, and `vlt-lint`'s `overlay_not_append_only` check only fires on **verbatim heading duplication** — so a subsumed overlay section persists silently as a shadow definition. Ship an **overlay-subsumption pass** in `vlt-upgrade` Step 3 (Conventions — overlays + baseline): after refreshing a base, diff each overlay section against the new base; where the base now covers the addition, prompt to retire the overlay section and record `overlay-subsumption` in `migrations_run` + the upgrade ledger. This filing is the first real round trip of local-prototype→upstream; without the retirement path, every future upstreamed overlay leaves a shadow.
- **Consumer acks.** Skills are module-owned, so the `depends_on: frontmatter@3` bumps ride the normal skill refresh; `vlt-lint`'s convention-coherence check confirms the handshake post-upgrade.
- **Legacy pages.** No backfill required anywhere — absence = evergreen *is* the migration path. Ship the seeded-backfill guidance as an optional note (one capped judgment pass, ~10–15 pages, scoped to inherently time-sensitive categories), not a migration step.

## Latent bugs surfaced

1. **Overlay resolution is indirection-dependent.** `vlt-ingest`'s On Activation says to read `{conventions}/frontmatter.md` — it never names `{overlays}`. Overlay reach currently depends on the *base's* overlay note ("read together with this file") being followed. Make it explicit in every consumer's activation: "read `{conventions}/{name}.md` together with `{overlays}/{name}.overlay.md` if present." Cheap, and it is what the pressure-test's Slice 0 had to spot-check by hand.
2. **No overlay-retirement path in `vlt-upgrade`** — the subsumption gap above. Merge-not-replace preserves; nothing reconciles an overlay the base has absorbed.
3. **The version handshake has no overlay axis.** `depends_on: ["frontmatter@2"]` pins the *base*; a vault-local overlay addition is invisible to the convention-coherence check. Likely acceptable (overlays are deliberately unversioned local additions), but it should be a stated property, not an accident.

## Open design questions to decide module-wide

1. **Does the module ship Obsidian Bases at all?** Options: ship `ledger.base` only (this proposal's original shape); also upstream `wiki.base` (vault-grown, proven, currently local); or keep Bases vault-local and ship only the schema + skill lines, with the views as documented reference. The `bases` structure-map name only earns itself in the first two. **The 2026-07-06 owner ruling tilts this to the third option** — vlt-core itself is folding the views into `wiki.base`, so a shipped `ledger.base` would diverge from the reference vault on day one.
2. **Bases date-filter capability is assumed, not verified** — the pressure-test's Slice 0 flags `review_after <= today` filter syntax as to-verify. Fallback if unsupported: Horizon (sorted ASC) becomes the primary view and the `vlt-lint` past-due finding is the queue. Verify before shipping the Due-for-review view.
3. **One `review_after` definition across three surfaces.** The synthesis's sequencing note: the freshness key (this filing), the bell's enforcement/deferral schema (`…-091004`), and the attestation freshness semantics (`…-091005`) share the frontmatter surface and must be designed against `frontmatter.md` together — three uncoordinated overlays is the failure mode. Proposal: `frontmatter.md` owns the definition; the other two reference it.
4. **Escalation policy for an aging queue.** Local adjustment trigger: due pages unworked for two cycles → escalate. Module-wide, is that lint's job or an enforcement-kit tripwire (`…-091003`)? Lean tripwire — lint finds, it shouldn't also nag.
5. **When do the v2 keys land?** `source_type:` and `review_note:` are parked; decide at a future `frontmatter@4` against usage evidence, not now.
