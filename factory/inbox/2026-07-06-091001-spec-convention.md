# The spec convention — a named home for inter-partner contracts, before the third consumer forks the format

_Filed from the `vlt-core` vault after the 2026-07-06 vault-evolution run (gap analysis → brainstorm → six parallel pressure-tests → synthesis) confirmed the council flag carried open through **two partner mints** — "give 'the spec' a named convention home BEFORE a third consumer appears" — now has a live fork risk: a **second proto-spec already exists** (the Creative→Chef meal-plan-format handoff, 2026-06-21). The pressure-test plan (`problem-solution-2026-07-06-082253-spec-convention.md`) is the design source; the vault-side mint runs from it as the **blocking pre-step to the next partner mint**. What's filed here is the module-side half: ship the convention stock so it stops being local divergence. This filing is unconditionally ripe — no evidence gate applies. Siblings in this batch: `2026-07-06-091003-enforcement-kit-derive-first.md` (the tripwires.yaml format takes this schema as its pattern donor) and `2026-07-06-091004-no-boundary-without-a-bell.md` (this convention adopts the enforcement/bell frontmatter block when that lands)._

## Problem statement + evidence

The vault has exactly one durable cross-partner contract artifact — the Health Coach→Chef nutrition spec (`_agent/handoffs/2026-06-13-health-coach-to-chef-nutrition-spec.md`) — and it is held consistent only by two partners' shared memory and manual relay discipline. There is no artifact *class* for it: no defined home, no frontmatter schema, no supersession rules, no mechanism binding a spec change to consumer notification.

- **The carried flag is real and escalating.** `_agent/mint/decision-log.md:62` (Health Coach mint): "'Spec' has no convention home yet — fine as a transient hand-off payload, but if specs ever persist/get cited across sittings, give them a named convention home." `decision-log.md:89` (Chef mint): flag **reinforced** — the Chef is the second consumer; "give 'the spec' a named convention home BEFORE a third consumer appears, so Health and the Chef don't grow two divergent notions of it."
- **The spec already behaves like a versioned contract without the machinery.** Revised in place twice (2026-06-20 calorie/protein revision; 2026-06-27 floor clarification), each with a hand-written "What changed" section and a *manually authored* dispatch relay entry. Practice invented versioning and notification — informally, on goodwill.
- **The fork risk is materializing, not hypothetical.** `_agent/handoffs/2026-06-21-creative-to-chef-meal-plan-format.md` is a second format-defining, multi-sitting contract doc ("live as of the week of 2026-06-21") sitting in the same untyped directory among four genuine one-shot handoffs. The class is acquiring members whether or not it gets a name.
- **The deadline is structural, not soft.** Retrofit cost is step-wise in consumer count: at n=2 it's a frontmatter edit; at n=3+ it's reconciling divergent notions of the format across partners *plus* the convention *plus* re-teaching. The third consumer arrives at the next partner mint — that is the fork point.
- **Root cause (Five-Whys, pressure-test):** the module has no mechanism converting a carried council flag with a stated trigger into a scheduled mint before the trigger fires. That generalized fix is carried below as an open question; this filing ships the specific convention.

## The decision and its rationale

**Composite: minimal convention + push/pull notification + reference-implementation retrofit + mint-time consumer lock.** Scored 29/30 in the pressure-test's decision matrix against six criteria (fork-closure, mechanism-not-goodwill, cheapness, upgrade durability, no-overclaim, deadline fit). Rejected alternatives, and why:

- **"Auto-notify" — ruled architecturally impossible.** The vault has no daemons or watchers; everything runs inside skill-invoked sessions. A hook-based true auto-notify (PostToolUse diffing spec files) is brittle (path-glob coupling), upgrade-fragile (hooks live outside the module bundle), and oversized for one instance. The honest mechanism is **push-MUST + pull-SHOULD**: on version bump the author MUST append one `vlt-dispatch relay` entry per listed consumer in the same session; a consumer citing a spec SHOULD re-check its `version` against the last version it consumed. Both are procedural rules bound to existing write paths — checkable now by inspection, later by lint — and "auto" appears nowhere in the convention's language. Redundant pair: push survives a consumer that never runs; pull survives an author that forgets.
- **Registry file** (`_agent/specs/registry.md`) — rejected: a second source of truth for `consumers`, a classic drift generator.
- **Overlay-only** (a `type: spec` stanza in `frontmatter.md`) — rejected: buries a *class definition* inside a field-reference doc; supersession and notification rules have no home there; discoverability ("read `spec.md` before writing a spec") is the point.
- **Spec-as-wiki-note** (inherit `wiki-supersession.md`) — rejected: a spec is a contract with an owner and consumers, not knowledge with sources and trust grades; wiki supersession has no consumer-notification concept.
- **Defer until n=3** — rejected: the deadline logic *is* that retrofit cost steps up at n=3; deferral is the failure mode dressed as prudence.
- **Full build with lint enforcement in v1** — rejected as the wrong slice: lint checks are named follow-ons, not dependencies.

Two load-bearing design facts: (1) the convention **codifies practice, not invention** — the reference spec conforms with **zero body changes**, the strongest evidence the schema is right-sized; (2) the conventions layer already models the pattern — `wiki-supersession.md` itself carries `version: 1` / `consumers: [...]`, so this strengthens an existing handshake rather than adding a new mechanism.

## Exact module-side changes to ship

1. **NEW `skills/vlt-setup/assets/governance/_meta/conventions/spec.md`** — the convention, shipping stock. Contents:
   - **Class definition + boundary:** a spec is a *durable, owned, versioned cross-partner contract* — authored by one partner, consumed by ≥1 other, cited into durable artifacts, revised over time. Explicitly distinguished from: a **handoff pointer** (transient, closes on pickup), a **handoff doc** (one-shot payload in `_agent/handoffs/`), a **wiki note** (knowledge, governed by `wiki-supersession.md`), and **BMad's SPEC kernel** (`bmad-spec`) — the term is overloaded three ways; the convention defines its meaning precisely.
   - **Home path:** `_agent/specs/` (agent zone → upgrade-durable by construction), created lazily on first spec.
   - **Frontmatter schema:** `type: spec`, `title`, `owner` (authoring partner slug), `consumers` (list of **partner slugs**), `version` (integer; bump only on changes to targets/constraints/rules — not typos or prose), `supersedes` (prior spec path, structural rewrites only), `status` (active/superseded), `created`, `last_updated`.
   - **Two `consumers:` semantics, stated explicitly:** on a *convention file*, `consumers:` lists **skills** acked via `depends_on` (the existing handshake); on a *spec artifact*, `consumers:` lists **partners** notified via dispatch relay. Same key, different registries — the convention owns this disambiguation.
   - **Supersession rules:** parameter changes → in-place revision at the stable path + version bump + a "What changed" changelog section (mirroring the reference spec's own six-week practice, and preserving relay's stable-path idempotency); structural rewrites → new file + `supersedes:` pointing back (mirroring `wiki-supersession.md`'s never-silent principle).
   - **Notification rule:** push-MUST + pull-SHOULD as decided above, with the exact relay invocation (`vlt-dispatch relay (to-slug, gist, spec-path)`, one per listed consumer, same session as the bump).
   - **Mint-time consumer lock:** any mint or capability change that makes a partner consume an existing spec MUST add that partner to the spec's `consumers:` in the same change. This is the anti-fork mechanism placed at the only moment a third consumer can appear.
   - **Its own convention frontmatter:** `version: 1`, `consumers: [vlt-mint, vlt-dispatch]` (add `vlt-lint` when the follow-on checks land).

## Upgrade/migration path for existing installs

- **vlt-core (the install that minted it locally):** vlt-setup's skip-if-present rule means the shipped `spec.md` will *not* clobber the vault's minted base; the baseline stash refreshes to the shipped version, so any local delta trips `convention_base_divergence` until reconciled. If the module ships this filing's text faithfully, the diff is zero and the divergence self-clears; otherwise `vlt-upgrade` Step 3.3 surfaces it for overlay-lift or upstream — the machinery already handles this case with no new code.
- **Fresh installs:** get the convention stock via the governance bundle; `_agent/specs/` appears on first spec.
- **Installs with existing proto-specs:** add one idempotent, **human-gated** item to `vlt-upgrade` Step 3.5 (*Migrations*): scan `_agent/handoffs/` for spec-shaped docs (revised in place, "What changed" sections, or ≥2 relay entries pointing at the same path) and *offer* the retrofit — `git mv` to `_agent/specs/`, one-line pointer stub at the old path (append-only records stay untouched), conform frontmatter, zero body changes. Never auto-move: spec-vs-handoff is a judgment call. The vlt-core retrofit (nutrition spec → `version: 3`, `owner: health-coach`, `consumers: [chef]`, `status: active`) is the reference implementation and the dry run of this exact procedure.

## Latent bugs surfaced

1. **File moves vs parallel worktrees.** The vault runs parallel sessions in git worktrees; a `git mv` in main leaves stale copies at the old path in every live worktree, which a parallel session can silently keep writing to. Any convention or migration that moves a load-bearing file should note this (the vault-side plan handles it by not touching worktree copies and stubbing the old path). Generalizable to every future relocation migration in `vlt-upgrade`.
2. **Shipped-skill examples coupled to live artifact paths.** `skills/vlt-dispatch/SKILL.md:193` hardcodes a real vault artifact's path (`_agent/handoffs/2026-06-13-…`) as its worked example — a vault-side file move strands the module's own documentation. Worked examples in shipped skills should use placeholder paths (`_agent/specs/{date}-{owner}-to-{consumer}-{slug}.md`), never a specific install's artifacts.
3. **Relay idempotency across a move.** Relay dedups on doc path; moving a doc resets the key, so an un-drained open pointer at the old path and a fresh relay at the new path can coexist. The pointer stub keeps the old link resolving, but the migration offer in `vlt-upgrade` should re-point any *open* dispatch pointers at move time.

## Open design questions to decide module-wide

1. **Carried-flag scheduling (the root cause).** A council flag with a stated trigger condition ("before a third consumer") is a deadline nothing schedules — this one survived two mints on luck. Should `vlt-mint`'s Phase 2 gate check open decision-log flags whose trigger the current mint would fire, and block until they're resolved? Cheaper variant: seed carried flags as tripwires in the enforcement-kit's `tripwires.yaml` (sibling `2026-07-06-091003`), making the deferral pay for itself with a wire.
2. **Does the class generalize to "contracts"?** Loop profiles (`vlt-track`) and format handoffs (the Creative→Chef meal-plan format, candidate instance #2) are adjacent. Ruling from the pressure-test: do **not** pre-generalize — test the convention against a real second instance first, then decide whether a "contracts" superclass earns itself.
3. **Where does notification-drift enforcement live** — a `vlt-lint` Step-2 check, a computed "tripped wires" line in `vlt-dispatch ledger`, or the enforcement-kit's derived counters? All three read the same records; pick one home before any lands twice.
4. **Escalation trigger, pre-agreed:** if a spec version bump ever ships without its relay entries, the procedural MUST has failed once — promote the lint/ledger enforcement from "scheduled follow-on" to "next mint."
