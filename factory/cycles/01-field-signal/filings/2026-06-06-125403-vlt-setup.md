# vlt-setup — friction notes from a fresh install

_Recorded 2026-06-06 after a clean `/vlt-setup` run into an installer-built vault (`vlt-sandbox`).
No prior Vault state; installer had written `config.toml` + staging dirs._

Overall: setup went smoothly. SKILL.md is thorough, the merge scripts are idempotent and
scoped to `vlt` only, the "skip if present" governance copy is clean, and the fresh-vs-reconfigure
branch made the state obvious. The notes below are friction points and drift risks, ranked.

## Real friction

### 1. Dependency check gives false negatives
SKILL.md says to check companion skills by looking in `{project-root}/.claude/skills/`. That check
reported `deep-research` as **MISSING** — but it's actually available as a host/global skill (the
Researcher can reach it). The detection method doesn't account for host-provided skills, so a literal
reading produces a spurious "missing dependency" warning to the user.

**Fix options:** check the actual skill registry rather than a project dir, or soften the instruction
to "absent from project skills *and* not host-provided."

### 2. `vault_structure` default map lives in prose only → drift risk (biggest one)
`module.yaml` defines `vault_structure` with `default: {}`. The actual default map exists in three
places that must stay in sync:
- the SKILL.md markdown table (hand-transcribed into the temp answers JSON during setup),
- whatever built-in fallback the runtime skills carry,
- the materialized copy written into `config.yaml`.

No single source of truth. Adding a logical path (e.g. `templates`) means updating the table, the
skills' fallbacks, and trusting setup to re-materialize it correctly.

**Fix:** put the canonical map in `module.yaml` (or a shipped asset) and have setup read it, rather
than relying on the agent to copy a markdown table correctly.

### 3. Installer's `[object Object]` wart is real
`_bmad/config.toml` literally contained `vault_structure = "[object Object]"`. SKILL.md correctly says
to ignore it (Vault reads YAML), and it was ignored — but it's a landmine for anyone debugging
"why is my structure broken?" who inspects the TOML first.

**Fix (optional):** surface a one-line acknowledgement in the setup confirmation summary so the user
sees it called out rather than discovering it cold later.

## Minor

- **SKILL.md density.** Long; the never-clobber / don't-run-cleanup warnings repeat several times.
  Safe, but leans hard on careful reading. The two operationally-load-bearing traps —
  `uv run` (not bare `python3`) and `{project-root}` being a literal token in config *values* but
  requiring the resolved `$ROOT` in shell *args* — could be hoisted to the very top.
- **Dates.** Scripts can't generate dates, so the agent stamps seeded files' `created:`/`last_updated:`
  from session context. Works, but correctness depends on the agent having today's date right.

## What should NOT change
- Idempotent, `vlt`-scoped merge scripts (anti-zombie, safe to re-run).
- "Skip if present" governance install — never clobbers a vault's own rules.
- Explicit fresh-install vs. reconfigure branch.
