# Field notes from the 0.2.0 → 0.3.0 upgrade (vlt-core)

Filed by: `vlt-upgrade` running in `vlt-core`, 2026-06-24.
Context: first real `vlt-upgrade` (own-the-apply, 0.2.0 → 0.3.0). Three upstream-worthy
signals surfaced while applying the 0.3.0 bundle to a live, evolved vault.

---

## 1. The contract dropped the dispatch-slice from Beat 2 but still depends on it

**Defect / coherence gap.** 0.3.0's `vault-operating-contract.md` Beat 2 (Orient) lists the
`capabilities/` folder as an orient read but **no longer lists the partner's open dispatch slice**
— it appears the capabilities read took the slot the dispatch slice held in the prior version.
Yet 0.3.0 still relies on partners draining their dispatch slice on orient: the **relay-when-done
reflex** (contract, *Sessions/hand-offs*) says "the recipient then drains it via the ordinary pickup
loop on its next orient." If Beat 2 doesn't tell partners to read their slice, relayed hand-offs are
never picked up — the dispatch bus silently stalls.

**What vlt-core did:** re-grafted the dispatch-slice orient read into Beat 2 (alongside the
capabilities read) plus its mutation-license paragraph ("the one orient read that may mutate shared
state — draining checks an item off; deliberate, never an activation side-effect"). This is the one
intentional governance divergence recorded in the vault's upgrade ledger.

**Ask:** restore the dispatch-slice to the contract's Beat 2 orient list in the next module version,
so Beat 2 reads *both* the capabilities folder and the dispatch slice. Then vlt-core's divergence
folds back to zero.

---

## 2. The module ships per-skill `.decision-log.md` build cruft into the installed surface

**Defect.** Many shipped skill dirs in the module source carry a `.decision-log.md` (BMad build-time
authoring metadata: `phase: build`, `classification`, `last_touched`). On `vlt-upgrade`'s
own-the-apply merge-copy, these 10 files were dragged into the installed vault — and one of them
**clobbered vlt-core's `vlt-mint/.decision-log.md` relocation stub** (the pointer that says "mint
history moved to `_agent/mint/` — don't write here"). The relocation discipline (filed 2026-06-13,
already shipped) is undermined by the module still shipping these.

**What vlt-core did:** removed all 10 build-log files from the install and restored the vlt-mint
relocation stub.

**Ask:** exclude per-skill `.decision-log.md` from the installed/shipped surface (gitignore or an
installer/copy exclude), so it stays a module-dev artifact and never lands in a vault. Bonus: this is
exactly the failure mode the relocation stub warned about — confirms the stub's value.

---

## 3. `merge-help-csv.py` is brittle against unquoted-comma rows minted in the field

**Friction.** vlt-core's live `_bmad/module-help.csv` had two rows (`vlt-agent-health-coach`,
`vlt-lint`) whose free-text fields contained commas but were **not quoted**, so the row had more
columns than the header. `merge-help-csv.py` hard-fails parsing the target before it can preserve
local mints — the upgrade's registration step was blocked until the rows were hand-fixed.

These rows were written by `vlt-mint` (the partner mints) and by a skill's own help-row authoring.
The root cause is field-quoting at write time.

**Ask (either or both):**
- Make `vlt-mint` / help-row authoring **always quote** free-text CSV fields (description, args,
  produces) when writing `module-help.csv`.
- Make `merge-help-csv.py` more tolerant — e.g. surface the offending row(s) and skip/repair rather
  than aborting the whole merge, so an upgrade isn't blocked by one bad field.

---

## Aside (not a defect): `vlt-track` is a local op worth upstreaming

vlt-core runs a `vlt-track` operation skill (the shared personalized-extraction loop hand — design a
protocol, log progress, review/adjust over weeks; calling partner supplies the profile + voice). It is
**absent from 0.3.0** and was preserved as a local mint. With 0.3.0's invariant-based personalized-
extraction firewall now shipped, `vlt-track` fits cleanly as a domain op that opts into the widening
per its mint. Candidate to upstream as the canonical longitudinal-loop hand.
