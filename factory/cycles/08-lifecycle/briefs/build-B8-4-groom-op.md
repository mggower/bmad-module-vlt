# Build #B8-4 — the groom op

The arc's motivating deliverable (evidence-debt ruling 2, owner overrule on record: the
groom capability is what prompted kicking off Arc 8 now). B8-3 shipped the contract
surface — the six-rung ladder, the three verbs (**promote / compress-to-latest-form /
retire**), the reflex layer, the safety model's shipped home — and left the verbs on a
manual-pass interim ("Until the groom op ships in the vault's installed version…",
contract `:212`). This build ships the op: **`vlt-groom`**, an upstream operation skill
(never minted into partners) that runs an end-of-need groom pass over one partner's
memory files, producing an **approval-gated diff grouped by the shipped disposition
types, one-line rationale per item, approvable per class — never a monolithic deletion
wall** (A9). Bond material is intimate; nothing is ever silently deleted — every act
obeys the shipped safety model (operating contract, *Hygiene and grooming — the safety
model*).

All rejected alternatives in the parent filing are settled — do not re-litigate. The
read-before-brief pin was honored against primary evidence: the full pre/post-groom
state at vlt-core commit `b00db0a` (read-only). What the prototype actually did — the
method this op codifies: pre-groom `thread.md` 29,752 B + `identity.md` 18,309 B → post
9,632 + 5,984 B plus a 2,142 B `reflexes.md` (21 rules, the filed ~63% cut); full
post-groom **replacement files staged in a `groom-proposal/` working directory**, then
applied **verbatim** (proposal == applied, byte-identical, verified by diff); one commit
pairing proposal + apply; `groomed:` + `archive:` watermarks set, `archive:` a git
reference to the pre-groom commit; standing reads compressed to latest-form-only with
grounds + falsifiers kept; episodic narrative retired to git history; the run performed
**by the partner itself, in its own sitting** (the commit is partner-attributed). Nothing
below is reasoned from the filing's summary alone.

## Brief-time dispositions (headless — each judgment call recorded here with its reasoning)

1. **Trigger model: INVOKED-ONLY — D2's interim default adopted; this brief does not
   argue otherwise.** *(Deferred question: "trigger model (scheduled vs invoked)".)* A
   groom is invoked by the user ("groom the librarian" / `vlt-groom {partner}`), or
   proposed by the partner at a natural seam (end-of-sitting, cap pressure, a
   correction-as-signal recurrence) and run only on the user's go — proposing is free,
   executing is invoked. No scheduled run, no tripwire-fired execution: the gate needs
   the user present, and invoked-only puts the user there by construction. **The
   decide-once hygiene-execution idiom (D2's composed ruling, this brief its home):
   *hygiene machinery may detect and suggest; only an invocation executes.* B8-5 adopts
   this idiom or records an owner-ruled divergence.** (A B8-5 wire's `surface_text` may
   *suggest* a groom; it never runs one.)
2. **The legal writer: the partner being groomed, at the wheel of its own sitting — the
   op is the procedure, never the writer.** *(A9's LEGAL WRITER question: reconcile the
   upstream-op ruling with the contract's own-zone single-writer rule.)* The
   reconciliation: partner memory is the partner's **own zone** (contract *Capabilities*,
   `:224` — own-zone writes are that partner's alone; `:229` "no cross-partner writes").
   An upstream op skill that wrote another partner's memory from outside would cross that
   line. So `vlt-groom` runs **inside the target partner's sitting**: invoking "groom
   the librarian" activates the Librarian, who runs the op on its own files — the same
   seat every operation skill already occupies (contract `:239`: ops run within a
   sitting, append their own log entries, never own the session note), and the seat the
   prototype actually used (the `b00db0a` groom is partner-attributed). The op is
   upstream **procedure** (shipped, upgrade-refreshed, single-homed — the ruling stands);
   the **writer identity** is the partner. Consequences, binding on the builder: the op
   never grooms a partner other than the active one; a **wiki-rung promotion** surfaced
   by the pass is rendered in the diff as a proposed **Librarian hand-off** (relay),
   never a direct wiki write (ladder row, contract `:210` — single-writer holds at the
   wiki lane too); the partner's **SKILL.md is untouchable** by a groom (rebirth is
   council territory, contract `:218` — the two-tier line).
3. **The gate: the user, in-conversation, over a staged proposal — per-class approval,
   per-item pull-out.** *(Deferred question: "diff-approval surface"; A9's rendering
   mandate.)* The approval surface is the conversation (invoked-only guarantees the
   user is present), backed by **staged full replacement proposal files** in a transient
   working directory (the prototype's `groom-proposal/` idiom) so the user can also read
   real files or a real `git diff` before ruling. The in-chat rendering is **grouped by
   disposition class — promote / compress-to-latest-form / retire — one line of
   rationale per item, with per-file pre/post byte counts**; each class is approvable
   or declinable as a unit, and any item can be pulled out of its class individually. A
   monolithic unclassified diff is a build defect (A9: "a ~30K deletion wall is not
   review"). The gate's authority is the **user, not the council**: the shipped safety
   model makes mechanical lossless-by-reference acts council-free and interpretive
   rewrites legal as an approval-gated diff — a groom pass runs the whole proposal
   through the stricter branch (one gated diff covers both), and no council convenes.
   Apply = the approved material lands **verbatim from the proposal** (proposal ==
   applied, the prototype's verifiable property); declined or unapproved material stays
   byte-identical in place.
4. **The decline disposition: an item-level decline writes a one-line inline marker on
   the surviving entry; marked items do not re-propose unless their content changes.**
   *(A9's DECLINE question, against the lint-has-no-memory precedent.)* The precedent,
   grounded: `vlt-lint`'s reports are append-only and never re-read
   (`vlt-lint/SKILL.md:72`), and its `flag_for_human` findings carry no record of a
   human's "no" — so the same declined finding re-surfaces every run, and the roundtable
   predicted the same fate turning this gate into ceremony. The fix: **a declined hunk
   is a ruling, and the ruling is recorded in the material itself** — the surviving
   entry gains an inline marker, `*(groom: declined YYYY-MM-DD — <the user's one-line
   reason>)*`, written as part of the applied diff (a decline is a write: keep-with-
   marker). **Re-proposal rule:** a marker-bearing item is excluded from subsequent
   groom proposals unless (a) its content has changed since the marker date (git shows),
   or (b) the user explicitly asks for a full re-argue. Two decline granularities,
   deliberately different: an **item** decline means "keep this" — durable, marked; a
   **class** decline means "not this pass" — session-scoped, unmarked, and it
   legitimately re-proposes next groom. The marker lives in the partner's own file
   (single home, travels with its item, retires with it) — **no groom ledger, no
   decline registry**: the safety model's "never in a new ever-growing ledger" clause
   rules those out.
5. **Codified vs judgment.** *(Deferred question: "what of the manual prototype's method
   is codified vs left to judgment".)* **Codified — the pass's mechanics:** (i)
   pre-flight: memory files' uncommitted changes are committed first, so `archive:` has
   a real reference (every append pairs with a commit — the safety model's premise; the
   op verifies rather than assumes it); (ii) read the three memory files whole plus
   their git history — never summaries; (iii) classify **every** item against the
   ladder's entry criteria (contract `:201-211`) into promote (with target rung) /
   compress-to-latest-form / retire / keep, skipping decline-marked items per
   disposition 4; (iv) stage full replacement proposal files; (v) render the grouped
   gated diff per disposition 3 and stop; (vi) on approval, apply verbatim, write
   `groomed:` + `archive:` (the pre-groom commit reference) per `frontmatter.md`'s
   Hygiene watermarks, delete the staging directory, append a partner-tagged **`groom`**
   `{log}` entry (a new log type, coined at the op per contract `:130`'s non-exhaustive
   rule), one line in the sitting's session note, one commit. **Judgment — never
   codified:** the classification calls themselves (dead vs merely quiet; which rung),
   the wording of compressed latest forms and of rationales, cap arguments, how much of
   `## Set aside` retires, whether `identity.md` compaction is worth proposing this
   pass. The op constrains *form and safety*; the partner supplies *judgment* — that
   split is the prototype's own.
6. **Scope of a pass: the three memory files; `capabilities/` excluded.** identity.md +
   thread.md + reflexes.md (the ladder's homes — reflexes participates via the cap's
   edit-one-out and promote-in/retire-out; the cap's enforcement posture already names
   this diff as its render surface, `frontmatter.md:218`). `capabilities/` files are
   contracts, not memory — no rung homes there; excluded, and `vlt-lint`'s
   `write_scope`/family duty over them is untouched (cross-filing ruling 4's split not
   re-ruled).
7. **R1 — not applicable, with one note.** No rule, check, or finding class ships ahead
   of its mechanism: the decline-marker vocabulary ships in the same build as its only
   executor (the op). The contract's own interim sentence (`:212` manual pass) is
   *reconciled*, not deleted (F3) — the manual pass stays legal for small in-sitting
   acts; per-vault, `:212`/`:216`'s "in the vault's installed version" phrasing
   self-resolves on upgrade.
8. **R3 — not applicable.** The groom renders no check findings: its diff items are
   proposals whose legal responses exist by construction (approve / decline / pull out,
   at the gate). The deferred (f) lint classes whose legal response *is* this op remain
   deferred (B8-3 disposition 1) — shipping the op is what makes them buildable later,
   but none ship here.
9. **A13 — the op creates no accumulating file.** The proposal staging directory is
   transient — deleted on apply and on abort (its content is byte-identical to the
   applied files; git carries the history); decline markers live inline in existing
   memory files and retire with their items; the run's records are the existing
   surfaces (one `{log}` entry, one session-note line). No groom ledger exists or may
   be created (disposition 4).
10. **R4 — the walk, with one declared structural coverage.** The enumerations a new
    skill joins: `.claude-plugin/marketplace.json` `skills[]` (package-lint C5 enforces
    one-to-one with `skills/vlt-*` dirs), `module-help.csv` (a row), README's roster
    ("14 skills in all" → 15, plus the roster table). The skill-asset manifest needs
    **no widening — declared structural**: `verify-skill-manifest.py`'s scope is derived
    by walking every shipped `vlt-*` dir (its docstring: "never a hand-kept list"), so
    `vlt-groom/` enters the net by construction. No vital enumerates op skills. One
    consumer-shaped grounding addition: `vlt-groom` writes `groomed:`/`archive:` per
    the frontmatter schema, so it joins `frontmatter.md`'s `consumers:` and acks
    `frontmatter@8` (F5) — a consumer addition, **not** a rule change: no version bump,
    no re-ack walk of the other eight.
