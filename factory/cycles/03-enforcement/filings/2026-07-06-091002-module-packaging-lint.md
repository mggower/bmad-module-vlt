# Pre-tag packaging lint — retire the release-cruft defect class at the factory boundary (hard gate: before the 0.6.0 tag)

_Filed from the `vlt-core` vault after the 2026-07-06 vault-evolution run's gap analysis found the same packaging defect class shipping in **every release 0.3.0→0.5.0** and a CIS pressure-test hardened the fix into a four-assertion-group `tools/package-lint.py` spec. This filing is itself **step 1 of the plan** (the plan's M1) — it carries the full assertion spec plus the two owner rulings the build needs. Unusually, the change lives **entirely in this repo**: no vault-side artifact ships. One of six filings landing together; siblings `2026-07-06-091004-no-boundary-without-a-bell.md` (this lint is that doctrine's factory-side worked instance) and `2026-07-06-091003-enforcement-kit-derive-first.md` (the field-side counters — same doctrine, disjoint substrate)._

## Problem statement + evidence

Every tag since v0.3.0 has shipped at least one instance of a **known, fully-specified packaging defect**, each caught downstream by vlt-core's `vlt-upgrade` and hand-fixed at the cost of a full inbox→capture→build round-trip per variant:

- **0.2.0→0.3.0** (`vlt-core/_agent/upgrade-ledger.md`, `[2026-06-24 12:30]` entry): 10 stray `.decision-log.md` build artifacts removed by hand ("Cleanup" line); two live `module-help.csv` rows (health-coach, vlt-lint) with unquoted commas fixed by hand — both already flagged in that entry's "Notes / to upstream".
- **0.3.1 / 0.4.0** (ledger `[2026-06-24 15:04]`, `[2026-06-26 08:46]`): each apply carries a manual exclusion pass (`.decision-log.md`, `__pycache__`, `*.pyc`, `reports/`, `.DS_Store`) — the class is *managed* per-upgrade, not retired.
- **0.4.0→0.5.0**: the live `module-help.csv` carried the legacy `after,before` header, requiring build-13's in-place migration (`canonicalize_header`, now `merge-help-csv.py:61`).

All three classes are *declared* as standing rules in this repo's `CLAUDE.md` ("violations here have bitten before" — CSV canon at lines 53–56, no-`.decision-log.md`-in-tree at lines 59–61), yet the release boundary (lifecycle step 6, `CLAUDE.md:29–32`: bump both version strings → ff-merge → tag → push) has **no mechanical check of any kind** — no CI, no hooks, no lint script, no `tools/` dir (verified 2026-07-06). Five Whys bottoms out at: **the release boundary has no bell** — for all three classes the enforcement stage is `declared`, never `checked`, and the defects are regenerated by tooling outside any build's scope (the BMad module-builder writes `.decision-log.md` every build; upstream templates still carry `after,before` — ruled out of build-13's scope).

The decisive diagnostic finding: **two ship surfaces**. `.gitignore` protects the git archive, but the primary consumption path — `vlt-upgrade`'s own-the-apply — is a **filesystem copy of the working tree** (`CLAUDE.md:59–61` says so itself). A check designed against "what git tracks" silently misses the worst class.

## The decision and its rationale

**Ship slice 1 before the 0.6.0 tag:** a tracked `tools/package-lint.py` + `CLAUDE.md` wiring + negative-test fixtures. The pressure-test's option table (feasibility × both-surfaces coverage × skip-resistance) rejected the alternatives:

- **CI on tag push** — post-boundary bell; checks the archive only, missing the working-tree path entirely. Deferred to slice 3.
- **Pre-commit hook blocking `.decision-log.md`** — wrong trigger point: the artifact *legitimately exists mid-build*; only its presence at release time is a defect (R3: certain false positives if mis-scoped).
- **Ship the lint inside `vlt-setup/scripts/`** — rejected outright: it is a factory tool; shipping it violates the factory/field split.
- **Fix the generator** (patch bmad-module-builder) — off-limits per "What not to touch"; upstream defects file to BMAD-METHOD.
- **Script alone, unwired** — reverse-brainstorm's #1 guaranteed-failure mode. In a no-CI, agent-driven repo the CLAUDE.md procedure text *is* the execution substrate, so wiring the invocation into step 6 is enforcement, not documentation.

Three load-bearing design rules (each the inversion of a guaranteed-failure): **(1)** wire the invocation into the procedure; **(2)** single-source the CSV canon from `merge-help-csv.py` — a local copy makes the enforcement tool the next drift site; **(3)** scope to release time, never commit flow. And one coverage rule: **assert on the working tree on disk, not the git index** — the single choice that covers both ship surfaces at tag time.

## Exact module-side changes to ship (slice 1)

**1. `tools/package-lint.py`** (new file; new tracked `tools/` dir — see owner ruling 1). ~100–150 lines, PEP 723 inline metadata like the merge scripts (needs `dependencies = ["pyyaml"]` for group C; run `uv run tools/package-lint.py`). Per-group PASS/FAIL lines, a one-line summary suitable for pasting into the release commit, exit non-zero on any failure. Four assertion groups:

- **A — on-disk cruft (working-tree check, not git-index):** fail if any `**/.decision-log.md`, `__pycache__/`, `*.pyc`, or `.DS_Store` exists **on disk** under the shipped surface (`skills/`, `.claude-plugin/`). Note: this fires **today** — `skills/vlt-setup/scripts/__pycache__/merge-help-csv.cpython-312.pyc` is on disk right now.
- **B — CSV canon, single-sourced:** the header of `skills/vlt-setup/assets/module-help.csv` equals the `HEADER` constant **loaded from `skills/vlt-setup/scripts/merge-help-csv.py`** (lines 38–52; hyphenated filename → load via `importlib.util.spec_from_file_location`, never a duplicated list). Every data row parses to exactly 13 fields via the `csv` module; free-text fields (`display-name`, `description`, `args`, `outputs`) are quoted **in the raw line** per the always-quote standing rule (`CLAUDE.md:53–56`).
- **C — module.yaml resolves + versions agree:** `skills/vlt-setup/assets/module.yaml` parses as YAML; `module_version` present (currently line 4); equals `.claude-plugin/marketplace.json` → `plugins[0].version` (currently line 16 — note it is **not** top-level; assert exactly one plugin entry before indexing). The governance bundle home `skills/vlt-setup/assets/governance/_meta/` exists and is non-empty (governance-SSoT standing rule).
- **D — tag intent:** optional `--expect-version X.Y.Z` asserts both version strings equal the tag about to be cut.

**2. Negative-test fixtures** (unit-verify at rest, per lifecycle step 5): copy the shipped surface to a temp fixture; seed one violation per class — a stray `.decision-log.md`, an `after,before` header, an unquoted description containing a comma, a version-string mismatch, a malformed row (wrong column count) — assert the lint fails each (5/5) and passes the clean tree.

**3. `CLAUDE.md` wiring** (two edits): **(a)** amend lifecycle step 6 (`CLAUDE.md:29–32`): before tagging, run `uv run tools/package-lint.py --expect-version X.Y.Z`; tag only on exit 0. Optionally record the PASS line in the release commit message (makes skipping visible). **(b)** amend the Git & publishing note (`CLAUDE.md:67–73`): the release-commit surface enumeration (`skills/`, `.claude-plugin/`, README, LICENSE) gains `tools/` — pending owner ruling 1.

**Slices 2–3, named but deferred (evidence-triggered, R6 scope freeze):** `tools/release.sh` wrapper (lint → bump both strings → ff-merge → tag → push as one command — makes the tag unreachable without a pass) + optional pre-push hook on `refs/tags/v*`; GitHub Action on tag push; teaching `vlt-upgrade` to *report* what it excluded (auto-drafted inbox filing). Escalation trigger: **any** packaging defect shipping in ≥ 0.6.0.

## The two owner rulings this filing carries (resolve at capture/M2)

1. **`tools/` tracked vs. gitignored.** Plan recommends **tracked + public**: the lint is a shipped doctrine artifact — the enforcement tool *is* documentation of the release contract — at the cost of the one-line Git & publishing amendment above. Gitignoring it keeps the publishing note pristine but makes the enforcement tool itself invisible dev-cruft.
2. **Arc placement / build numbering.** Opening build of the next arc vs. a standalone maintenance build (Arc 2 closed at build-13). Pure sequencing call — the only hard gate is **M3+M4 (script + negative tests green, CLAUDE.md wired) before the next `git tag`**.

## Upgrade/migration path

**None — deliberately.** Nothing ships to vaults: no skill body changes, no convention bump (so no version-handshake re-ack), no overlay, nothing for `vlt-upgrade` merge-not-replace to reconcile. The consumer-side exclusion pass in `vlt-upgrade` stays **unchanged as the second bell** — it uniquely covers the residual post-tag gap (cruft regenerated between tag time and a later own-the-apply; R2). Field interaction is acceptance-only: the 0.6.0 upgrade-ledger entry on vlt-core is the regression probe (exclusion pass finds nothing; CSV canonical and quoted; `module.yaml` resolves). This filing archives per the standard lifecycle: build shipped **and** that live acceptance passed. Success metric thereafter: **zero packaging filings into `inbox/` for releases ≥ 0.6.0**.

## Latent bugs surfaced

1. **`vlt-upgrade/SKILL.md:45` under-specifies the exclusion list.** The shipped text mandates excluding only `.decision-log.md`; the wider list actually applied in the field (`__pycache__`, `*.pyc`, `reports/`, `.DS_Store`) exists only as session practice recorded in vlt-core's upgrade-ledger. A fresh session following the SKILL as written would ship the `.pyc` that is on disk right now. One-line fix candidate in `vlt-upgrade/SKILL.md` (a genuine vault-facing edit — small enough to ride along with this build).
2. **Live instance of class A today:** `skills/vlt-setup/scripts/__pycache__/merge-help-csv.cpython-312.pyc` — gitignored, but on the own-the-apply path. Delete at build time; the lint then keeps it out.
3. **Grounding correction:** build-13 (and the pressure-test) cite the canonical header at `merge-help-csv.py:36–37`; in current source that is the comment — `HEADER` is lines 38–52, `LEGACY_HEADER` line 58. Bind the lint to the **symbol**, not a line number.

## Open design questions to decide module-wide

1. **YAML dependency posture:** the merge scripts are `dependencies = []`; group C wants a real YAML parse. PEP 723 + pyyaml via `uv run` (recommended, matches the repo's uv posture) vs. stdlib-only line-scrape (weaker "resolves" semantics).
2. **Group A root scope:** does the shipped surface include repo root (README/LICENSE level — e.g. a root `.DS_Store`)? Cheap to include; decide once.
3. **`marketplace.json` `skills[]` ↔ `skills/` dir cross-check:** a drift class that has not yet bitten (though vlt-track's 0.4.0 upstreaming changed that list). Per the scope freeze: extension requires a recurrence — but decide now whether it is group C's natural fifth assertion or slice-3 material.
4. **Doctrine registration:** when `2026-07-06-091004-no-boundary-without-a-bell.md` lands its enforcement-frontmatter schema, should this lint be declared as the factory boundary's `checked_by`, making the module repo the doctrine's first fully-`checked` boundary? (Natural, but sequencing: this ships first; declare retroactively.)
